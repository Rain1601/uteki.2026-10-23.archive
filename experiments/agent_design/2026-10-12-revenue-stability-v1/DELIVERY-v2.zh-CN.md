# E6-R5a：修复证据选择的操作归属

2026-10-12。第三轮暴露的来源选择契约已修，保留所有原结果。原失败动作、独立边界和三次新鲜自主执行均已核验。本轮三次没有操作归属拒绝、均交付正确数据；但每次仍需要一次审核引用修订，**总纠错并未下降**。这两个结论分别成立，不用最终成功掩盖修订成本。

## 根因及本轮改动

原 R3 的七块原文在操作前均已完整读取。模型将两家公司材料放到一个 `delivery.blocks` 列表，并指定两个不同来源的 requirement。程序的语义是把这个列表给每个 requirement，而非按来源自动配对。原错误同时涵盖来源、scope 和未读情况，没有指出实际冲突。后来不补读，只分开选择便成功，支持本次归属契约诊断。

修复四处共同机制：

1. 决策协议 v6 解释“同一列表应用于每项任务”，不同来源、报告版本、不同选材集合分别操作。同源同冻结 scope、确实需要同样材料的多个任务仍可共用一次操作。
2. Query Skill v17、模型实际提示和 schema 字段说明同步。没有公司、金额、特定原文块或本地实验路径默认值。
3. 来源选择先检查任务归属，再区分 context 不存在、冻结范围不符、块来源不符、块未读完、重复块。返回稳定错误码和当前登记的来源/任务标识。来源冲突不再误导为必须重读。
4. 全部检查通过后才改选择。整次拒绝保持旧选择；程序不替 Agent 分配块，不自动拆分，不放宽来源或完整读取限制。

来源选择只检查归属合法，不判断相关性或材料充分性。语义仍由运行 Agent、双审与 Codex 独立原件验收分别负责。`select_records` 的运行逻辑未改；本轮补充它同样广播列表的说明，未把历史记录分组问题全部追认为已修。

## 验证方式

- 原 R3 冻结动作重放：七块确已读；原混合操作仍被拒绝，返回两组来源冲突；原两次合法拆分通过。使用当时输入的读取目录，不拿最终磁盘状态冒充此前已读。
- 独立合成测试：跨公司、同公司修订报告、同来源不同 snapshot、同 block ID 跨来源、未读和重复块分别检查；验证同源共用合法，拒绝不产生部分写入，明确诊断进入下一轮后能拆分恢复。归属专项 11 项通过。
- 相关回归 57 项通过，包含上述专项及正文交付、计划追加、角色/worker、公共协议；另模型适配与原生 envelope 等关联检查通过。不用这些数量代替真实内容验收。
- v2 三次均从零运行：保留同一收入问题、完整数据集、模型、预算与标准，只冻结本轮四个执行文件/Skill 的变化。执行代码和 Skill 在三轮期间保持不变。Codex 没有提供选择结果或答案。
