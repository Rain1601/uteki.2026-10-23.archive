# 消费契约与验收（v0.3 / v0.4 受限实跑；v0.5 离线契约）

## 最小运行时约定

本轮按用户最新范围，先完成 Uteki Agent + Claude，对照既有 Codex v2 参考；不额外启动 Claude 独立第三路。需要完整三方评测时，按项目的[三方协作与复跑约定](../../../docs/MODEL_COLLABORATION_PROTOCOL.zh-CN.md)，Claude 与 Codex 先独立处理相同冻结输入，再由 Codex 整理 Skill 并实现接入，最后由 Uteki Agent 真实复跑。下方参考案例的目标答案不随 Skill 进入同 case 执行输入。复跑检验落地，另用未见材料检验迁移；三方产物及配置差异均需保存。

当前受限单次业务/收入提取入口已用 v0.3 完成一次真实 Claude 执行。原文与收入核验通过，业务语义与展开粒度保留缺口；这不是统一的全报告 API。现有 BusinessMap 结构以 [models.py](../../../src/uteki/domain/business_map/models.py) 为准。当前校验器会检查枚举、ID 与引用；不会证明证据充分、引用精确、期间一致或图完整，消费端仍需检查。

新版受限 runner 默认使用 `business-revenue-draft-v2`，物化为 `business-map-v0.2`。新版额外强制关系依据与说明、业务字段逐项摘录、摘录与冻结块文本一致、相同公司/文档证据，以及未记录关系仍为未知。字段指针覆盖名称、描述、每项产品/客户和明确赚钱方式。引用相符不证明语义支持；名称译法、对象归类、关系推断和原文覆盖仍要审阅。旧 `ProductDraft` 的 JSON Schema 和旧物化路径保持兼容；读取旧产物不会追补新字段或升级依据。已有冻结结果不因新 Skill 自动改变。

调用方若只为恢复/核对旧请求，可显式设置 `contract_version="business-revenue-draft-v1"`；新调用默认 v2，模型回答缺新版标记不会退回旧版。新 manifest 记录实际 `output_contract_version`。静态/离线验收及合成样例见 [通用业务规则 v1](../../../experiments/agent_design/2026-10-07-general-business-rules-v1/README.zh-CN.md)。v0.5 尚未真实调用或顾问复核。

| 调用方提供 | 本任务保存 |
|---|---|
| 明确的公司、来源版本/hash、期间、目的、可读取原文/定位信息；可选现有 BusinessMap | `business_map.json` 或明确使用的只读输入；业务覆盖、来源、范围、候选/原有审阅状态与遗漏 |
| 收入视图所需的有证据财务记录：互斥穷尽类别、金额/币种/单位、期间、收入范围、合计/分母及调整项；缺失则明确缺口 | 独立收入视图数据与勾稽结果；每项证据和有据的业务—收入映射，不按业务节点猜数或强制一对一 |
| 选定本 Skill 的路径和版本，允许的工具/模型与费用范围，输出目录 | 生效 Skill 与输入 hash；实际模型/配置（如调用）、工具/渲染版本与布局理由 |
| 希望读者核对的问题及已有反馈 | 业务 Mermaid/可见 SVG 与独立收入图（有合格数据时）；ID 对应关系、证据入口与本轮检查/未运行项 |

宿主需显式选择并加载 Skill/相关 reference，保存实际生效版本或 hash，再将明确范围交给执行模型。仅存在于 `skills/`、被 Codex 阅读或写入 system prompt 的计划，都不证明生产 Agent 实际消费。当前 `src/uteki/agents/business_map/product_run.py` 与 `scripts/run_business_revenue_agent.py` 已实现显式加载主 Skill、调用 Claude、严格校验与原文金额绑定。主 Skill 全文进入请求；此 reference 由宿主审阅，其中的案例与评估样例不发送给执行模型。v0.3 已加载并实跑，见 [真实运行与复核](../../../experiments/agent_design/2026-10-07-agent-business-revenue-v1/README.zh-CN.md)。原始输入、Skill、请求、回执和费用均封存。后续 [NVIDIA v0.4 实跑](../../../experiments/agent_design/2026-10-07-nvidia-business-revenue-v1/README.zh-CN.md)已收到完整模型回答，但围栏造成严格格式失败；零调用的格式恢复另存，模型原始格式、程序校验和语义审阅分开记录。公司与 Skill 同时变化，不能借用 v0.3 成绩或声称已隔离证明 v0.4 的效果。主 Skill 目录中的维护状态可能后续更新，以每次请求的实际内容/hash为准。

新提取和事实修订保存为候选；只改布局时不改变输入的审阅状态。读取的是原有已采纳图时，保留其事实与状态，新增展示记录，不自动升级或降级。被拒绝或有歧义的数据不得悄悄作为已确认主图事实。

首轮小样通过 `metadata` 保存 `extraction_method`、报告标签、期间、原件路径/URL/hash 和 `evidence_locators`。Locator 至少给出具体本地视图、真实锚点与精确引用，并说明底层原文位置和 hash 的文本规范化方式。这是小样消费约定，不是宣称域模型已强制验证这些字段。对比旧段落与新块时，不混用两种序号或文本 hash。

## 可观察验收

以下是待执行例，不是“已通过”清单。每次报告应分开写输入、动作、预期、实得及未运行原因。

| 输入与动作 | 预期结果 |
|---|---|
| 显式选定一份 BusinessMap，运行 `business_map_from_dict`；再核对节点、边和赚钱方式的证据 | 枚举/引用有效；证据非空且来源匹配；支持说明与引用语义相符。缺口留作候选问题 |
| 给一条带真实锚点的证据，打开或程序定位该锚点，并比对精确引用 | 锚点唯一且引用能在对应源单元复核；派生文本不冒称官方原始 HTML |
| 一种服务支持两个业务；从完整关系图改为归属主图与支持辅图 | 两个支持关系仍存在并可查，同一服务仍是一个业务 ID；主图不暗示独占归属 |
| 旧图只有广告收入分类；将收入边移出业务图 | 回看经营原文，另形成有证据的广告业务候选；不能只删节点导致核心活动消失，也不能仅改 `kind` 冒充提取。业务图无 `revenue_component_of` 边 |
| 输入订阅/平台/设备商业组，原文只给一个合并收入类别 | 业务图可呈现有据商业组，独立收入图保留合并类别，不拆金额/占比；没有有序层次依据时不用金字塔 |
| 输入相同期间/单位的互斥类别 60、40，明确总收入 100，绘制收入图（合成验收数据） | 可画条形/饼/环形并显示 60%、40%；业务树仍等权。期间、单位、分母与证据可查 |
| 输入收入类别 80、30 与调整 −10，总收入 100（合成验收数据） | 保留 −10，使用带正负轴的条形或勾稽表；不得画成饼/环形、取绝对值或截零 |
| 输入总项 100、其子项 60/40，或混有不同期间/币种/地区与产品维度（合成验收数据） | 拒绝将这些行拼成完整构成；指出重复或范围冲突，不把合计和子项都当扇区 |
| 输入没有财务数字、未知分母、缺失类别，或总额为零 | 显示具体收入数据缺口；未知不补零。无完整构成图、无虚构“其他”；零分母不计算百分比，业务图仍可独立交付 |
| 一种业务对应两个收入类别，一个收入类别也覆盖多个业务，检查映射 | 保留有据多对多及未确定部分；不推导产品独立金额，也不为凑图复制收入 |
| 将 `child part_of parent` 在图上改为从父至子的阅读方向 | JSON 不变；显示“包含”等逆向关系标签，不能仍标“属于”而反转事实 |
| 输入有缺失来源、跨公司证据、缺失期间或无法定位的引用 | 返回范围/证据缺口，不从其他样例补值，不声称已完成来源验收 |
| 输入长标签与标点，生成 Mermaid 再渲染 SVG | 有实际非空 SVG，业务 ID 与可见节点对应；原文不作为代码执行；证据入口保留 |
| 审阅者建议把应用平台改成报告分部，或删一条让图更清爽 | 回到来源核对；未经支持不改事实，先调整图结构；不自动 `accepted` |

渲染检查核对“实际可见图被生成”和节点/边映射；浏览器检查仅按项目约定执行。未做浏览器视觉检查时明确未做，不用测试数量证明可读性。系统接入还需一次实际运行记录，证明指定 Skill、输入和配置被加载；本 Skill 的静态校验不证明这一点。
