# 业务组成覆盖规则 · v4 计划

## 已观察问题

Google 业务 r2 的模型复核通过，但独立验收发现 Services 的主要产品/平台定义缺失。所交付收入类别不能代替业务组成。原题、公司和原件不变，旧包保留为失败证据，不人工填回正确材料。

## 顾问讨论与 Codex Review

Opus 在同一私密会话第二轮完整回复（HTTP200/end_turn，估算$0.069316）。认可“区分问题维度”是通用规则，提醒不能把完整相关列举升级为全文所有产品的并集。提出需求维度、证据角色、逐分部覆盖、原块完整性、最后最小化的顺序。

Codex 采纳该顺序，先使用已有 requirement.description、原文引用和复核 rationale 表达，不新增一套仅由模型自报的标签协议来冒充语义保证。通用工程校验继续保证范围、引用、完整已读和逐项复核；独立原件验收检查内容是否实际足够。阅读组元数据不能替代未交付的正文。

## 当前改动范围

只更新 Data analysis_evidence 任务理解、查询 Skill 与内容复核提示：

1. 问业务组成时，先找原文定义的主要产品、服务、活动及所属分部；收入/变现分组不足以替代。
2. 完整性限于问题粒度和原文定义性列举；不搜集全文所有产品提及，不默认读取整章。
3. 逐分部确认身份、业务范围及必要限定，再做最小化；不能因为某产品不是独立收入项目就删除。
4. 只问收入时，仍只取数字及其必要口径，不强制附产品清单。

不加入公司名称、期望答案、原文块ID或Codex选段。原件和提取结果不做特例修补。

## 验收

当前v3剩余云业务/回购任务按已启动版本完成。v4以原问题重新执行六题：失败业务题需由模型自己找齐定义性原文；微软业务及两题收入必须不回归，云口径与回购限定仍保持。每题模型自审与独立验收分列，不以“没有报错”或模型pass计完成。
