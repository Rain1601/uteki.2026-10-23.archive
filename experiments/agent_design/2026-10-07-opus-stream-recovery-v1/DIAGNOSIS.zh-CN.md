# Opus 未交付：排查与修复

本轮用户要求检查日志、修复 Opus 未交付，并继续其他公司。已找到与旧请求匹配的 AIHubMix 成功记录；问题是本地没有完整收到响应，不能写成 Opus 没有执行。

## 日志证据

| 层级 | 观察 |
|---|---|
| 本地旧调用 | 241.047 秒后非超时 HTTP 传输异常。没有可用正文；未进入输出格式/业务校验。 |
| 供应商控制台 | 同窗口唯一匹配的 Opus 5.5，45,669 输入、13,971 输出 tokens，288.188 秒，成功，记录费用 $0.462096。 |
| 渠道 | 旧 Opus 走 VertexAI；Sonnet 基线走 AWS。渠道不同是实际观察，不能据此断言渠道造成断连。 |
| 关联依据 | 模型、时段、输入量及一次派发记录匹配。本地未保存响应请求 ID，无法给出精确 ID 对账证明。 |

[供应商核对记录](../2026-10-07-sonnet-opus-business-ab-v1/provider-console-reconciliation.json)只保存这两条相关记录，未保存账户余额、联系方式或凭据。旧本地运行、未知费用记录和预算不改写，补证与新恢复运行分别保存。

客户端显式超时为 300 秒，超时错误与本次 RuntimeError 分支不同。没有找到该调用路径的 240 秒本地限制。长时间非流式连接被中间网络或网关断开是合理解释，但具体节点尚无法确认，不能宣称 AIHubMix 有固定 240 秒限制。

旧适配器通过 `client.post()` 读取完整正文后才记录 HTTP 状态和请求 ID；即使头已收到，正文读取失败也可能没有留下头信息。因此旧记录的空状态不证明服务端从未发过响应头。

## 已实现的修复

1. 收到响应头就记录白名单状态、请求 ID、阶段和耗时，随后读取正文。断流仍保留已知信息。
2. 支持显式后台流式接收。只累计可见文本，收到完整结束事件后统一做 JSON、范围、出处与金额校验，页面不增加打字效果。
3. 缺少最终用量、流被截断、错误事件或无完整结束标记都不能当作成功。费用未知不补零；没有自动重试。隐藏思考、签名、请求头和异常正文不落盘。
4. 流式模式允许显式 600 秒总等待上限；旧非流式默认及 300 秒边界保留。49 项离线检查通过，含正常流、断流、异常、私密内容过滤与旧请求字节一致。

Anthropic 官方提示长时间空闲连接可能被网络中断，并建议长请求采用流式接收：[长请求说明](https://platform.claude.com/docs/en/api/errors#long-requests)。这支持修复方向，不能证明本次具体断连节点。

## 恢复实验的范围

[冻结协议](protocol.json)：对旧 Opus 请求正文只改 `stream=false → true`，本地等待上限从 300 秒改为 600 秒；同一 Alphabet 原文、Skill v0.3、high effort、16k 输出上限及输出契约。执行代码的版本差异全部保留。新请求受本轮排查授权，单次估算上限 $1，零自动重试；不复用旧失败目录或旧顾问账本。

恢复成功后才可核对内容质量。它与旧 Sonnet 的接收方式和执行代码版本不同，称恢复后对照，不偷换成旧的纯模型单变量实验。供应商统计不提供本地丢失的回答正文，也不能替代新运行内容。
