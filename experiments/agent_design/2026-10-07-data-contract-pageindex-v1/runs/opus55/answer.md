**标注约定**
- 【事实】：来自你们给的代码核查摘要或已核实的 PageIndex 资料。
- 【建议】：我的意见。
- 【假设】：示例中的虚构内容。
- 【待验证】：需要实验或用户确认。

我没有读仓库，也没有运行任何东西。

## 结论先行

1. 【建议】草案方向正确。最大缺口不在 schema 字段，而在三处：
   - 消费结果没有"覆盖声明"。
   - 结论没有"陈述类型"。
   - "可得、可算、有归因、可解释"没有分开。AMD 那次的错误正出在这里。
2. 【建议】PageIndex 先学方法，用在自有 block 树上。只有当范围内确有真实 PDF、且自有解析缺少结构时，才加本地 SDK 适配器。Cloud 暂不作为默认路径。
3. 【建议】不需要新建注册中心。在 discover_catalog / get_schema 的返回中加少量字段即可。前提是 MCP 和 Agent 真正读取这些字段。

## 1. 业务描述与三层契约

### 1.1 更准确的业务描述（建议用语）

> Data Agent 把冻结来源加工成若干**有身份、有版本、有血缘的数据产品**。每个产品自带结构、语义与访问说明。
> 对一个自然语言问题，Data Agent 按说明选择访问方式，返回**带覆盖声明的证据包**。证据包内每个元素都能回读到冻结来源的块、字符区间或单元格。
> Analysis 只在证据包上写结论。每条关键陈述标明它是来源事实、计算结果、管理层观点还是研究推断，并按类型接受不同检查。

这段话把"生成一堆文件"换成了"产品 + 证据包 + 陈述类型"。它没有改变业务范围。

### 1.2 三层契约：缺什么，哪里过度

| 判断 | 内容 |
|---|---|
| 缺：覆盖语义 | 工具和证据包要说明读了哪些节点/页/块、哪些被裁剪、哪些没查。"没找到"不等于"未披露"。 |
| 缺：可得性四态 | 每个缺口或结论要区分：①数据在来源中；②可由已有数据按公式算出；③来源有明确归因；④属于商业解释。AMD 错误是把"无③"说成"无②"。 |
| 缺：表示等价 | 同一事实的 DB 行、JSON、精编句子，要能通过 `representation_of` 指向同一个事实 ID，避免重复计数。 |
| 缺：版本失效策略 | 新快照只产生新版本。旧引用继续固定在旧 hash 上，并标记"有更新版本"。 |
| 缺：消费者绑定 | 每个说明字段要写明由哪个工具读取、执行时如何校验。否则就是被复制后无人消费的 schema。 |
| 过度：统一大 payload | 不必让所有产品共享全部字段。公共头保持小，其余交给各自的 schema_ref。 |
| 过度：access_methods 写成自由文本 | 只引用已有工具名和参数 schema。权限由工具强制，说明里的字符串不授予任何权限。 |
| 过度：陈述级证据规则放进产品说明 | 这类规则属于 EvidencePackage / Analysis 的验收协议，不属于产品描述。 |

### 1.3 六种产物最小对照

| 产物 | 结构（已有/拟议） | 语义要点 | 访问方式 | 现状 |
|---|---|---|---|---|
| 原文块/表格 | SourceBlock、SourceLocator（已有） | 原样文本；表格带表头、期间、单位、脚注 | read_source、DocumentReader outline/search/read | 【事实】已实现；HTML 可到块/单元格，图像 OCR 部分未运行 |
| 结构化事实 | ResearchRecord（已有） | 主体、指标、期间、单位、口径、维度、available_at；何时不可合计 | query_facts（typed plan→参数化 SELECT） | 【事实】已实现；QueryDataPort 侧为候选，发布侧另走 ResearchDataPort |
| 双语精编 | 中/英两份，共用一套 claim 锚点（拟议） | 导航与背景；每句关键事实挂源锚点；翻译本身不是证据 | 按章节读取；关键句回读原文 | 【事实】业务要求已存在；完整执行器未完成。双语保留 |
| 业务图 | 节点/边，每条边有 evidence_refs（拟议细化） | 区分"来源披露的关系"与"推断关系" | ResearchDataPort 业务图读取 | 【事实】发布侧已有；与 QueryDataPort 未贯通 |
| 导航索引 | DocumentIndex 父子、起止块（已有）+ 节点摘要（拟议） | 摘要只用于导航，不能作为证据 | outline；拟议增加树导航工具 | 【事实】SEC 主要到 item 级 |
| 证据包 | EvidencePackage 八类、derived_from（已有）+ coverage（拟议） | 本次查询范围、已读、未读、陈述类型 | Analysis 经 load_reviewed_data 消费 | 【事实】已实现血缘与类型校验 |

## 2. 示例

### 2.1 最小公共产品说明

【假设】以下所有 ID、hash、指标名都是占位，不代表真实数据。

```json
{
  "artifact_id": "facts:<company>:<filing_id>",
  "artifact_type": "structured_facts",
  "version": "v3",
  "schema_ref": "research_record@<schema_version>",
  "scope": {"entity": "<company>", "periods": ["<FY_a>", "<FY_b>"],
            "source_versions": [{"snapshot_id": "<snap>", "sha256": "<hash>"}]},
  "record_grain": "一个主体×指标×期间×维度组合的一个数值",
  "semantics": {
    "not_comparable_when": ["口径不同", "单位/分母不同", "重述前后混用"],
    "not_summable_when": ["维度含合计行", "分部与抵销项并列"]
  },
  "status": "candidate",
  "coverage": {"tables_extracted": ["<table_block_ids>"],
               "known_not_extracted": ["脚注中的非表格数字"]},
  "access_methods": [{"tool": "query_facts", "input_schema_ref": "<ref>",
                      "limits": {"page_size": "<n>"}}],
  "evidence_contract": "每行带 source_locator，可经 read_source 回读到 cell",
  "derived_from": ["source:<snap>"]
}
```

字段落点（【建议】）：
- `schema_ref`、`semantics`、`access_methods` 扩充现有 get_schema / discover_catalog 的返回。
- `coverage` 和 `status` 是新增字段。
- 由 MCP 的 discover_data 原样暴露这些字段，不另建目录。

### 2.2 "业务相关资料补证"查询计划

【假设】问题是"<company> 的业务是什么、如何赚钱"。范围为用户已选定的 `<filing_id>`。没有选定真实公司或财年，也不使用任何真实数值。

| 步 | 工具 | 参数要点 | 产出 |
|---|---|---|---|
| 1 | discover_data | entity、filing 限定在已选范围 | 可用产品列表及 coverage |
| 2 | get_data_schema | 事实产品、业务图 | 指标定义、维度、不支持项 |
| 3 | read_source(outline) | 冻结来源 | 业务描述节、分部附注所在节点 |
| 4 | read_source(search) | 模型给出的同义词组；程序限定范围 | 命中块，并说明是否被截断 |
| 5 | read_source(read) | 命中块及相邻表格/列表 | raw_text / raw_table 证据 |
| 6 | query_facts | 分部收入类指标，按分部维度，与表格同一期间、同一口径 | 记录及其 cell 锚点 |
| 7 | read_source(cell) | 回读第 6 步的单元格 | 值、表头、单位核对一致 |
| 8 | 业务图读取 | 分部→产品→客户类关系 | 每条边的 evidence_refs |
| 9 | 组装 EvidencePackage | derived_from 指向块/单元格 | 附覆盖声明：已读节点、未读节点、裁剪情况 |
| 10 | request_missing_data（如需） | 写明缺什么、属于四态的哪一态 | 补证请求，不直接写结论 |

## 3. PageIndex 评估

### 3.1 对 Uteki 的具体价值

【建议】真正有用的是方法：在层级树上，由模型阅读节点标题和摘要，逐层选择分支。它能弥补"字面短语匹配"在同义表达、跨节问题上的缺口。

它解决的是"去哪里读"。它不解决以下问题：
- 证据定位：本地 SDK 只到页级。
- 表格会计语义。
- 完整性：没访问的分支不能证明内容不存在。

### 3.2 三条路径对比

| 维度 | A 方法移植到自有 block 树 | B 本地 SDK 适配（PDF） | C Cloud |
|---|---|---|---|
| 输入 | SEC HTML、PDF、未来新闻/博客均可（基于自有块） | 【事实】仅 PDF，无本地 OCR | PDF；块接口可能有 bbox |
| 定位精度 | 保持块、字符区间、单元格 | 【事实】页级，需映射到块 | 【事实】块+bbox；旧索引可能没有块信息；无会计语义 |
| 来源冻结 | 已有 hash 与快照 | 【事实】不归档原件和 hash，需自管映射 | 同左，且数据外发 |
| ID 稳定 | 自控 | 【事实】节点按遍历编号，重建可能变化 | UUID；节点同样不可依赖 |
| 权限 | 自有工具边界 | 【事实】context 只是提示，需自己校验 | 同左 |
| 成本 | 摘要/导航的模型费 | 【事实】无平台费，模型费另计 | 【事实】$0.01/页索引 + 存储（前 1000 页免费）+ 查询模型费；Uteki 未实测 |
| 成熟度 | 自研维护 | 【事实】0.2.10 Alpha | 厂商托管 |
| 主要风险 | 摘要漏信息 | Flash 可能拒绝；页→块映射失败 | 外发合规；块与 Uteki 证据双轨 |

### 3.3 三组差异，必须写进契约

- **页级与片段/单元格级**：PageIndex 本地返回的页范围只能作为导航结果。进入 EvidencePackage 之前，必须映射到 Uteki 的块和单元格。映射不唯一就记为失败，不能猜测。
- **索引与证据**：树摘要（包括由子摘要形成的父摘要）只能 `nav_only`，不能出现在 derived_from 的证据端。
- **导航与完整性**：导航结果要附"已访问节点 / 未访问节点"。只有对范围内所有相关节点做过穷举或关键词兜底，才可以写"该材料未披露"。

### 3.4 不同材料的建议

| 材料 | 建议 |
|---|---|
| SEC HTML | 走 A。在现有 part→item 下按标题细分到小节；为节点加 nav_only 摘要。不要把 HTML 转成 PDF 再喂给 PageIndex，那会人为制造页→块映射问题。 |
| 真实 PDF | 先确认它在范围内，并检查自有解析是否缺结构；确有缺口再试 B。 |
| 新闻/博客 | 篇幅短，扁平块 + 关键词通常就够，不值得建深树。重点是发布/获取时间、来源归属和快照。 |

### 3.5 用最小实验决定，不凭印象

【建议】三到四个实验组，同一题集，同一阅读预算（最多读 N 个块/页）：

| 组 | 方法 |
|---|---|
| A0 | 现有 outline + 字面短语搜索 |
| A1 | 块级 BM25 类关键词检索 |
| A2 | 自有 block 树 + 节点摘要 + 模型逐层导航 |
| B | 仅在有真实 PDF 时加入：PageIndex 本地 + 页→块映射 |

指标：
- 金标锚点召回（在预算内读到）。
- 引用锚点精确率。
- 覆盖声明是否诚实，即是否误报"不存在"。
- 页→块映射失败率。
- 成本与延迟。

**决策规则（事先写定）**：
- A1 若已能补上 A0 的失败题，就不做树导航。
- A2 只有在 A1 失败的题上有明显提升，且精确率不下降，才值得做。
- B 必须优于 A2，并且映射失败可控，才引入。

## 4. 查询路由

### 4.1 程序控制与模型选择的分工

| 程序强制 | 模型可选 |
|---|---|
| 公司/期间/快照范围，工具白名单 | 用哪些产品，先后顺序 |
| typed plan 校验与 SQL 编译、分页、限额 | 指标选择（限于 catalog 内）、同义词 |
| 锚点回读与 hash 核对 | 树分支选择、何时停止（须附覆盖声明） |
| 陈述能否标为"来源披露" | 解释的组织方式 |

### 4.2 路由规则

- **数值问题**：指标在 catalog 内 → query_facts → 回读单元格。
- **描述类问题**：outline → 关键词 → 读上下文。
- **关系类问题**：读业务图，再把每条边回读到原文。
- 需要多种产品时都要取。任何一种产品的结果都不替代原文回读。

### 4.3 冲突、缺数据与来源更新

- **原文与数据库冲突**：在"原文说了什么"这个问题上，以冻结原文为准。记录标记 `conflict`，生成更正请求。两个值都保留可见，不静默覆盖。
- **缺数据**：先按四态归类，再写清覆盖范围。之后发 request_missing_data。Web Search 只是发现入口；新来源必须经过抓取、冻结、提取，才能进入证据流程。第三方报道标为"报道称"，不自动成为已核实事实。
- **来源更新**：生成新版本，旧引用保持固定，后台批量重验并标出差异。

### 4.4 自由 SQL 是否必要

【建议】现在不需要。做法是：
- 把 typed plan 表达不了的问题记为 `plan_unsupported`。
- 积累真实样例后，优先扩充 plan 类型。
- 如果将来确需自由 SQL：只读、限视图、限行数，且返回结果仍须带记录 ID，以便回读证据。

## 5. "关键结论有依据"的验收协议

### 5.1 Claim ledger

【建议】Analysis 输出一张 claim ledger。每条关键陈述包含：
- claim_id
- 中英文本：双语共用同一组锚点
- claim_type：`source_fact` / `computed` / `management_view` / `research_inference`
- evidence_refs
- formula_ref

### 5.2 三层检查，彼此不能互相替代

| 层 | 问题 | 检查者 | 方法 |
|---|---|---|---|
| L1 可定位 | 锚点存在吗？ | 程序 | 快照 hash 一致；字符区间 substring 一致；单元格行列存在；表头/期间/单位齐全 |
| L2 被支持 | 证据真的支持这句话吗？ | 数值由程序比对；文字由盲评 | 值、单位、期间比对；语义上蕴含 |
| L3 无遗漏 | 必要信息覆盖了吗？ | 题目级清单 | 清单在运行前独立编写；每项要么被覆盖，要么在覆盖声明下标"缺" |

### 5.3 按陈述类型检查

| 类型 | 引用要求 | 检查 |
|---|---|---|
| source_fact | 原文块或单元格 | L1 + L2 |
| computed | 公式 + 每个输入的单元格 | 程序复算；输入逐一过 L1 |
| management_view | 原文块，表述写成"管理层称" | L2 检查归属是否准确 |
| research_inference | 前提 claim_id + 推理步骤 | 盲评检查前提是否成立、推理是否有效、是否明确标为推断。不要求原文逐字披露 |

### 5.4 额外规则

- **误报缺口计为错误**。例如来源有两年原表，却声称"无法计算贡献"。
- **不设固定缺口数量**。缺口只能由可得性检查产生。
- **评分契约写进题目**，包括精度、舍入和容差。DeepSeek -53.2% 那类误判属于评分契约问题。
- **schema 合格只证明 L1 的前提成立**，不证明 L2 和 L3。

## 6. 最小迭代与公平比较

### 6.1 最小迭代

【待验证】材料由用户指定一份已冻结快照。不默认任何公司或年度。

1. 一个数值问题。例如"两期某现金流项目的差额"。验收：
   - query_facts 取两期值，回读两个单元格。
   - 程序复算。
   - claim 类型为 computed。
2. 一个业务问题，例如"主要业务与收入来源"。验收：
   - 证据包含业务描述块、分部表单元格，以及业务图边的锚点。
   - 附覆盖声明。
   - L1 全部通过。
   - L2 由盲评完成。
   - L3 对照事先写好的清单。
3. 全过程走现有 MCP 链路：discover_data → get_data_schema → query_facts / read_source。每次实验保留独立的请求、产物和配置。

### 6.2 公平比较

- **题集**：多家公司，多种文档类型（HTML 年报、真实 PDF、短新闻），题型包括事实查找、表格、多处取证、计数/计算。不能只用同一公司的两个例子宣称泛化。
- **隔离**：金标锚点和答案单独存放，不进入索引、摘要或提示词。
- **同条件**：同一模型、同一预算、同一停止规则。
- **报告方式**：逐题结果，按题型分层，并报告独立事实数。例如"40 实例 / 6 独立事实"必须如实写出。
- **评审**：盲评，评审者看不到组别。

## 7. 成本与稳定性记录

### 7.1 调用记录字段

| 字段 | 说明 |
|---|---|
| call_id | 全局唯一。汇总时按它去重，同一调用不得重复计入 |
| phase | `index_build` / `query_plan` / `retrieval` / `source_read_extract` / `verify` / `judge` |
| index_version | 用于摊销：建索引成本 ÷ 使用该版本的查询数 |
| status | 成功 / 失败 / 重试。失败调用的费用照常计入 |
| cost_usd | 拿不到时填 `unknown`，在单独一栏汇总，不按 0 处理 |
| model / config_ref / tokens | 用于对应 Trace |

### 7.2 稳定性报告

- 分别报告数值一致率与 claim 级 L2/L3 通过率。
- 给出分布，不只给均值。
- 标注独立事实数。
- 重复运行只能暴露波动，不能证明稳定。不承诺"跑十次即证明"。

## 8. 最值得先做的一个行为变化

【建议】**让 Analysis 的每条关键陈述都进入带 claim_type 的 ledger，并且缺口只能由四态可得性检查产生。**

验收例子：
- 用已做过实验的那份现金流小节做回归用例（需用户确认可以复用该冻结快照）。
- 合格输出必须做到两点：
  1. 把"两期差额"标为 computed，引用两个单元格，并能由程序复算。
  2. 把"管理层未逐项归因"标为第③态缺失，同时**不得**声称该差额不可计算。
- 两条都由 L1/L2 判定。
- 这只是回归测试，不代表泛化效果。
