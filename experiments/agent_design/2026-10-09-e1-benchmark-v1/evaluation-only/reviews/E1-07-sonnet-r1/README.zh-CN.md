# E1-07：材料完整，跨版本查询被冲突检查阻挡

**独立内容验收 4/4 通过；系统流程仍为 `attempts_exhausted`，没有放行。** 冻结标准是四项，不是七项。这个结果不是少拿了财报材料，而是系统把题目要求保留的两个版本当成必须消除的单值冲突。

问题：比较 Microsoft FY2024 和 FY2025 两份 10-K 各自披露的 FY2024 三个报告分部收入，保留版本、单位、期间及解释差异的原文，不把重列当成自然业务增长。

| 分部 | FY2024 原年报的 FY2024 数值 | FY2025 年报的 FY2024 比较数 |
|---|---:|---:|
| Productivity and Business Processes | 77,728 | 106,820 |
| Intelligent Cloud | 105,362 | 87,464 |
| More Personal Computing | 62,032 | 50,838 |

单位均为 **百万美元**，观察期间均为 **2023-07-01 至 2024-06-30**。两列代表同一财年的不同披露口径。

我逐条检查六个原始数值节点、单元格、USD 单位、scale=6、分部 XBRL 维度与财年 context，全部与交付记录相符。最终也保留了两份报告各自的来源 ID/hash、报告期和可得日期，没有用新值覆盖旧值。

FY2025 原文明确解释：2024 年 8 月改变分部组成，特别将 Microsoft 365 的商业组成集中到 PBP，前期分部信息按 FY2025 管理口径重列。这段在本题是必需信息，已交付。两组数没有相加，也没有生成“自然同比增长”的计算。记录的 `accounting_basis` 字段本身仍只写 `reported_dimensioned`；重列身份由来源版本和这段原文共同说明，不能谎称已有单独的重列标签。

| 冻结要点 | 结果 |
|---|---|
| S1 原 FY2024 三个分部数值及单位 | 通过 |
| S2 FY2025 报告中重列的 FY2024 三个数值 | 通过 |
| S3 组成调整与前期重列的原文解释 | 通过 |
| S4 同期间、不同版本分别保留，不覆盖、不相加、不称自然增长 | 通过 |

流程为什么失败：数字查询以“分部 + FY2024 + 收入”为条件，同时查询两份报告。每个分部正确返回两条不同数值，程序因此打上 `record_ambiguous`，并保留 `requirement_incomplete:req_seg_rev_query`。模型审核认为材料完整，但程序检查阻止 `analysis_eligible`。第二轮仍走相同查询，未消除这一流程阻塞。

对只要一个数值的问题，这个保护是必要的；对明确要求比较两个披露版本的问题，应保留两个有来源限定的结果。不能采用“永远选最新”或无条件绕过冲突检查。独立内容通过没有覆盖旧失败状态，也没有伪造系统放行。

最终交付 **6 条结构化记录、5 块正文、2,171 字符**。正文包括两张相关分部表、两句表引导及一次重列说明。没有重复交付同份年报的 MD&A/附注两套表，也没有产品清单。评分中 767 字符标作整表附带数据；仍有其他年份、费用/利润等可裁切内容。固定粒度 focus 通过不等于达到严格最少字符，两份来源的不同值则是必需对比，不应去重掉。

两轮共 **30 次调用，估算 $2.886770**；输入 1,349,140 Token，输出 18,849 Token，未知费用预留为 0。全部 API 响应成功，任务失败属于查询语义与流程约束问题。最终 packet 文件 **181,737 字节**，不是 2,171 正文字符的同一计量口径。费用为估算，不是结算账单。

下一步应修复明确的多版本对比查询语义，保留单值查询的歧义保护，再复用或重新验证这些来源记录。无需 Codex 代替系统补答案。
