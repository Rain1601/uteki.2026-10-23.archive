# 本轮结果：事实稳定，说明与缺口仍会变化

完成两项任务 × 两套配置 × 两次独立重复，共八次真实请求。全部 HTTP 200、正常结束，无重试、续写或后台补写答案。各次响应 ID 不同，同配置重复的实际请求正文和配置哈希相同。

本轮 Sonnet 更快、合并质量门槛通过次数更多；DeepSeek 单次估算费用较低。两者都没做到每次正文完全相同，也都出现了说明或缺口判断的问题。这不是模型总体排名。

实际失分举例：DeepSeek 事实 R1 说无法核对非现金调整及分项构成，但原表 r7–r24 已有这些项目；R2 以缺少 2020 期初数为由否定跨年勾稽，超出了本题 2023/2022 范围。Sonnet 变动 R2 说无法判断各项对下降的精确贡献，但表格允许计算会计项目的同比贡献；不能仅因缺少管理层解释就否定这部分可计算内容。完整商业原因仍然需要其他证据。

这说明质量问题不只发生在数字里。`gaps` 也必须核验：不能把已经提供的信息写成缺失，不能为满足数量要求而补出没有依据的限制。盲评逐条证据及争议保留在[事实核对评审](review/blind-facts-scores.json)和[变动解释评审](review/blind-change-scores.json)。评分由一位隐藏模型身份的 Codex 代理完成，未经独立人工确认；不是供应商自身评分，也没有写入工作台人工评分。

## 精度要求的设计缺陷

DeepSeek 变动 R2 写出 −53.2%。真实变化为 −53.239831697…%，所以这是正确的一位小数舍入，不能称为算错。原评估容差是 0.02 个百分点，误差约 0.03983，故程序保留不通过。

题目没有告知需要两位小数或这个容差，只有隐藏评分规则写了门槛。这是本轮试题设计缺陷。原程序 7/8 的结果不重写，也不拿这一次精度失败证明模型算术更差。下一版应将小数位、舍入方式和单位直接写入公开输出契约。[独立协议审计](review/benchmark-audit.json)

## 过程与配置的对应

共享的是原始来源、同题输入和系统提示；八次调用各自有目录，独立保存开始记录、实际 HTTP 正文、配置、回执、结束状态和输出。两种 API 的正文封装不同，同一模型的重复请求正文一致。验证文件相同只表示相同程序得出相同检查状态。

当前是单次请求实验，没有模型选择工具和多轮执行轨迹。过程页的统一结构不能说明两边内部推理相同，也不能据此评价完整 Data Agent。未保存私有推理正文，仅保存供应商返回的用量计数；推理 Token 数也依赖渠道计量口径。

采样参数与未发送原因已显示在结果/过程页。Sonnet 的 Temperature、Top-P、Top-K 没有发送，因为其规格不接受非默认值；DeepSeek 的 Temperature 在思考模式无效，Top-P 明确为 0.95，Top-K 和 Seed 未发送。供应商实际生效值没有独立回显，不能把“请求已发送”升级为“内部执行已证实”。详见[配置与方法](README.md)。

## 下一轮先改什么

1. 明确精度规则；将缺口限定为经过证据核对的缺口，允许没有额外缺口时返回空列表；在请求前同时冻结评分实现、规则和测试。
2. 加入另一家公司或 20-F 小材料，以及与现金流不同的任务；分别检查提取、摘要、解释和业务关系。保持单次执行、检查后再继续。
3. 增加重复次数和独立人工复核后再讨论选型。固定模型别名、提示、输入和配置只能改善可追溯性，不能承诺服务内部版本、硬件与采样完全确定。若业务要求同一版本逐字相同，应读取已核验的冻结产物；重新调用模型则继续评估事实与结论的稳定性。

限制：本轮两个任务共用同一份 AMD 小节、每配置仅重复两次、不同模型用不同协议/力度/输出上限。评分规则先于调用冻结，但评估脚本在执行期间完成，未纳入执行前哈希锁。因此本轮是探索性试验，不是确认性统计测试，也没有证明跨公司、整份报告或完整 Agent 的泛化能力。
