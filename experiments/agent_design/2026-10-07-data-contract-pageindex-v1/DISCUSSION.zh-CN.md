## 业务目的

把原材料加工成有明确结构、业务语义、访问方式和来源的数据产物。让查询模型知道有什么数据、怎样取数、哪些地方没有覆盖；让分析模型能够回到具体材料，形成可核对的结论。

这包含两个独立验收目标：提取正确，以及消费正确。一个数值提取无误，查询时仍可能选错年份、单位、公司、会计口径或采用状态。

拟议的数据流如下。现有组件已实现其中一部分，完整多产物链路尚未验收：

```mermaid
flowchart LR
  A[年报 新闻 官方博客] --> B[版本化原文与具体片段]
  B --> C[事实 文档 业务图 索引]
  Q[问题及明确范围] --> D[按数据契约选择取数方法]
  C --> D
  D --> E[回读原文 组装证据包]
  E --> F[带依据的分析结论]
```

## 每类数据都需要契约

通常每一种产物类型维护一份版本化 schema，实例引用该版本，不在每条记录里复制整份 schema。schema 负责结构约束；模型还需要语义和操作说明。

| 说明 | 内容 | 能防止什么问题 |
|---|---|---|
| 结构 | 字段、类型、必填、关系、版本 | 缺字段、类型不一致、引用关系断裂 |
| 语义 | 一行代表什么，主体/期间/单位/口径，候选/核验/采用状态 | 错加不同单位，拿报告年份代替财务期间，把候选当已采用事实 |
| 消费方式 | 工具、参数与返回契约、范围、分页、限额、错误、回读证据方法 | 模型猜数据库表、调用错误工具、把部分返回当全部 |
| 来源与转换 | 原始快照、片段定位、父产物、转换或计算方法、运行版本 | 文本改版后引用漂移，计算值冒充直接披露 |

前三项组成使用说明；来源与转换贯穿全部产物。通过 schema 验证仍需检查事实、证据支持和覆盖。

一个最小[产品说明 JSON 示例](product-description.example.json)已保存。里面全部为占位符，仅用于讨论，不是已实现的新 API，也没有真实财务数值。

| 产物 | 已有基础 | 消费方法 | 待补齐 |
|---|---|---|---|
| 原文块与表格 | SourceBlock、表格结构、冻结快照 | read_source 的 outline/search/read/context/evidence | 各来源的实际定位精度及解析覆盖验收 |
| 结构化事实 | ResearchRecord、候选数据库、查询 schema | query_facts；typed plan 编译为参数化 SQL | 完整覆盖、内容核验与采用闭环 |
| 计算结果 | ComputedScalar、注册公式与操作数 ID | 受限计算工具与结果读取 | 更广的受支持公式与分析交接；不能默许任意口径计算 |
| 双语精编 | 产物契约；model_summary 证据类型 | 拟议章节读取、检索、逐陈述证据映射 | 完整精编执行器与验收，保留已有双语要求 |
| 公司业务图 | BusinessMap 契约和候选生成组件 | 按业务、关系和证据消费 | 通用主链路、跨年身份与正式采用 |
| 文档索引 | DocumentIndex 父子节点、原块范围 | 目录导航及原文回读 | 更细的导航/召回方案比较 |

JSON、Markdown、数据库是表示或存储方式。业务图与事实均可有 JSON 表示；它们不能因此被当成同一种语义对象，或被重复统计成独立证据。

现有 [Data MCP 工具说明](../../../src/uteki/interfaces/data_mcp/server.py)和 [get_data_schema](../../../src/uteki/interfaces/data_mcp/service.py)已覆盖发现、语义说明与查询。应在真实需要处扩充，而非重建一套平行入口。[证据契约](../../../src/uteki/domain/research_data/evidence_package.py)已有类型和派生关系。

## 多层索引该怎样分工

建议把三个导航层分开：

1. **资料目录**：按公司、材料类型、期间、知悉截止日和版本选材料。
2. **文档目录或主题入口**：找到可能相关的章节；一个主题可关联多个章节，不强行放进唯一分支。
3. **原文片段与表格定位**：读取段落、表格及必要上下文，再定位字符区间或单元格。

结构化指标目录和业务关系索引可以指向同一批证据。短新闻可直接走片段检索，不必凑足三层。

例如“所选年报里的谷歌业务是什么、如何赚钱”，需要同时读业务描述和分部披露；必要数字再通过事实查询取回，并核对分部口径。不是只用公司名跑一条 SQL，也不是把目录摘要直接当公司结论。本例没有选择实际财年，未在本轮生成谷歌业务结论。

## PageIndex 是否适合

**适合作为长文档导航和证据召回的候选方案。最终证据仍由 Uteki 的版本化原文与定位契约管理。**

当前核查固定在 commit `6d23caf416858f2ca136840305d1f479a86f6ef7`，包声明 0.2.10、MIT。开源版已经有本地索引、检索与 chat。默认 Flash 从 PDF 布局建立初始树，再可用模型优化、摘要；查询由模型选择阅读节点/页。源码新版树字段与在线旧示例有差异。[固定版本](https://github.com/VectifyAI/PageIndex/commit/6d23caf416858f2ca136840305d1f479a86f6ef7) · [Flash 源码](https://github.com/VectifyAI/PageIndex/blob/6d23caf416858f2ca136840305d1f479a86f6ef7/pageindex/flash/api.py)

| 选择 | 可能价值 | 主要代价或限制 | 当前建议 |
|---|---|---|---|
| 借鉴树导航方法，复用 Uteki 原块 | 保持 SEC HTML 的片段和单元格定位 | 需要验证更细索引、摘要与导航是否改善召回 | 适合先以现有材料做小实验 |
| 增加 PageIndex 本地 SDK 适配器 | 复用 PDF 建树与检索工具 | 本地入口为 PDF，无 OCR；引用到页；需要 Uteki 精细证据映射 | 当真实 PDF 场景需要时单独比较 |
| 接 PageIndex Cloud | 提供 OCR/图像处理、块读取与托管 | 新服务、成本、来源身份与版本映射；块仍需语义验证 | 当前不默认接入 |

本地页级、Cloud 块级是官方明确的能力区别；Cloud bbox 也不自动携带财务口径与单元格关系。[本地与 Cloud](https://github.com/VectifyAI/PageIndex) · [块读取接口](https://docs.pageindex.ai/sdk/documents#read-a-block-cloud)

本地节点按树遍历编号，不能把 node_id 当作跨重建不变的证据身份。当前本地存储流程保存文档元数据、树和页内容，没有替 Uteki 保存原始 PDF/hash。[节点与字段处理](https://github.com/VectifyAI/PageIndex/blob/6d23caf416858f2ca136840305d1f479a86f6ef7/pageindex/utils.py) · [存储实现](https://github.com/VectifyAI/PageIndex/blob/6d23caf416858f2ca136840305d1f479a86f6ef7/pageindex/local_store.py)

接入位置应是 `PageIndex 节点 → 已核对的源版本/页范围 → Uteki 原文片段`。HTML 与 PDF 不是可以靠页码自动等同的来源；映射无法验证时，应显示限制，不能补造坐标。树摘要只用于导航，最终依据回读原文。

一页对应多个块是正常情况，可先回读候选块集合，再定位支持陈述的部分。只有版本/内容对应或具体支持片段无法确定时，才判定精细锚定失败。摘要和索引可以保留在加工血缘中，但不能独自充当关键事实的根证据。

厂商 98.7% FinanceBench 来自 Mafin 2.5 系统，不能作为 Uteki 的预期成绩；较新的 OSS benchmark 仅覆盖 62 道正文事实查询，排除了表格、计算等任务。我们尚未在本项目实际运行 PageIndex。[Mafin 评测](https://github.com/VectifyAI/Mafin2.5-FinanceBench) · [OSS 评测范围](https://github.com/VectifyAI/PageIndex-OSS-Benchmark)

## 如何验收准确消费

| 层 | 检查例子 |
|---|---|
| 结构与范围 | 公司、原件版本、实际期间、来源策略和候选范围都来自显式选择 |
| 取数正确 | 查询使用 schema 中已有指标/关系；单位、维度和口径正确；缺记录不补零 |
| 定位有效 | 引用能读回原块，文字区间或单元格值匹配；表头和脚注可查 |
| 支持陈述 | 引用真正支持主体、时间和限定条件；管理层观点保留归属 |
| 覆盖 | 对照独立所需证据清单，检查遗漏、矛盾、分页和未访问分支 |
| 分析表达 | 分清直接披露、公式结果和研究推断；推断列明证据及假设，不声称原文直接证明 |

现有 SourceLocator 提供许多精细坐标，但多数可空；应按产物定义最低可接受精度。引用“存在”与引用“足够”分开判断。尤其是“整份报告未披露某事”，不能只凭一个片段或一次搜索无结果证明。

来源增加到新闻或官方博客时，继续保留获取快照、发布时间/获取时间、出处和归属。Web Search 用于发现材料，实际证据应进入同一获取、解析与定位过程。第三方报道与独立核实状态分开。

## 最小推进步骤

1. 用一份已有冻结报告跑通两种真实消费：一个数值问题、一个跨段落业务问题。模型先读契约，再取数并回读片段。错误期间、来源、单位和真实缺资料应有对应反例。
2. 按这两个例子补产物说明及验收。语义问题先由已有 typed plan 与工具处理，不增加任意 SQL 执行入口。两例通过只代表接口贯通。
3. 再冻结独立问题和证据清单，比较现有目录/短语搜索、改进关键词检索、PageIndex 导航。检索与最终回答质量分别记录；同时计算建索引、查询、回读/提取和验证费用。相同来源的索引费按实际复用次数摊销。

新闻/博客适配、完整精编与跨年业务图继续分步扩展，不因同用一种 schema 包装就宣称已经支持。

实验不能把“读 N 页”和“读 N 块”当相同成本。应在相同查询 token/费用预算下比较质量，再比较达到目标质量所需的成本与耗时。检索指标关注找回哪些原始证据；回答指标关注用这些证据是否得出正确、完整到约定范围的答案。两者分别测量。

## Claude 提出的增量，以及审核修正

值得采用的建议有四项：

1. 每个问题分别检查：数据是否在来源中、能否按公式计算、来源是否明确归因、结论是否需要研究判断。它们是可同时成立的独立维度，不是互斥四态。
2. 让中英文精编共享陈述身份和源锚点，分别检查语言表达是否保留相同事实与限定条件。
3. 明确哪些 JSON、数据库记录、图属性是同一事实的不同表示。可以引用同一个规范事实身份；不能把相似句子或跨来源报道自动合并成同一事实。
4. 产品说明中的每个字段都对应实际消费者和检查规则，避免只增加模型没有读取、程序没有执行的元数据。

Claude 的原文也需要以下更正，已保留原文而不回写：

| 原文建议/说法 | 审核后的处理 |
|---|---|
| coverage、status、陈述类型尚不存在 | 已有 EvidencePackage.coverage、MCP 状态和 Analysis fact/inference/unknown。应统一并强化已有机制，不能重建后称为首次实现 |
| read_source(cell)、schema 读取 BusinessMap、search 同义词列表 | 当前接口没有这些操作。用 evidence 或 context/read 回读表格，再按证据中的坐标定位；多个短语需多个受控查询。业务图仍有自己的消费边界 |
| query_facts 可自由按 dimensions/accounting_basis 查询 | 目前记录请求主要按 entity/metric/period/value_kind；分部 entity 可来自目录，但没有任意维度过滤能力。遇到现有工具不能表达的需求应返回限制，再决定扩展 |
| 数值示例直接使用现金流差额注册计算 | 现有注册公式没有这个公式。应选已支持公式，或另行登记现金流公式/明确独立核算步骤；不能伪造已支持能力 |
| 关键词补搜后可声明整份材料未披露 | 通常只能说“在指定版本、范围和方法下未找到”。完整非披露判断要更强的覆盖标准；搜索无结果不能独自证明 |
| 本地与 Cloud 都不保留原件/hash | 只核查了本地存储实现。Cloud 的原件保留与导出保证未核实；Uteki 应继续保存自己的来源快照 |
| PageIndex 本地 context 都不能强制范围 | 自有 Agent 的 context 辅助方法只是提示；内置 local chat(doc_id) 已有另一层 allowlist。应核对实际采用的接入路径 |
| 本地 SDK 必须比自建树质量更高才可用 | 也可能因覆盖真实 PDF 场景、减少维护或同质量更低成本而值得采用，需按真实需求比较 |
