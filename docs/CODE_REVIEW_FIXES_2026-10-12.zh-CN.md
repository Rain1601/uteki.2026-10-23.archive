## 1. 我们究竟在问什么

E6 的冻结业务 Query 是：以 2026-02-06 为可得截止日，仅根据所选 Microsoft 与 Alphabet 的 FY2025 10-K，分别提供两家公司 FY2025 和 FY2024 的公司整体收入。每项保留财年、准确起止日期、币种、单位和可定位原文。不计算增长，不合并公司金额，不展开分部。

预期交付是四项收入及足以证明它们的原文、日期、单位和出处。Data Agent 自行找材料、查询、阅读、选择并审核。Codex 负责实现与独立验收，不替运行 Agent 选块或补答案。

这轮没有重新执行该 Query。历史 V3 报告记载九次运行中八次最终交付、三次无恢复成功；另一次因输出截断没有交付。这是原报告结果，不是本次重新核验的成绩。现在发现验收脚本可能把磁盘材料误当作模型收到的内容，因此历史可见性结论必须用修正后的检查器重审。该缺陷本身不能证明历史答案错误，也不能证明模型确实看到了那些材料。

原问题、每次结果与历史费用：[V3 公开交付](../experiments/agent_design/2026-10-10-e6-repeatability-v3/PUBLIC_DELIVERY.zh-CN.md)。

## 3. 技术路径与选型

继续使用现有 Python 数据适配器与验收脚本、ArtifactStore 分页协议，以及现有网页模板和 JavaScript。此次问题没有证据要求更换模型、数据库、检索方案或引入 PageIndex。

| 选择 | 原因与边界 |
|---|---|
| 展示层隔离单条不可用记录 | 保住其他可用数据；证据读取层仍严格失败，不静默补数据 |
| 依据实际 SDK 输入验收可见性 | 文件保存成功只能证明存储；同一 Query、Scope、artifact 身份/hash 与实际输入才支持可见性判断 |
| 两个评测入口共用一个离线检查器 | 避免相同判定规则再次漂移；仅在 evaluation-only 中使用，不把评测答案传入生产 |
| 报告升级 v2 并绑定检查器 hash | 新旧判定可追溯；不覆盖旧运行与旧报告。公共 helper 精确加入 Git 保留清单，原始运行包仍私密 |
| 展示层兼容旧、新财务字段 | 保留历史证据，不改写原产物、不按公司或币种补默认值 |

## 4. 修复方法与验收证据

固定原输入与预期 → 找到最早偏差 → 提出可证伪的原因 → 用最小反例区分原因 → 在责任层修正机制 → 回放原反例 → 验证独立输入与拒绝边界。

例如 R22：假设“磁盘有文件被误判成模型读过”。保持文件完整且 hash 正确，只让模型输入保留未读取引用。旧实现通过、新实现拒绝，支持这个机制判断；再用真实分页读取通过作正向对照。不是把失败样本改成通过，而是修正判断何时有资格通过的标准实现。
