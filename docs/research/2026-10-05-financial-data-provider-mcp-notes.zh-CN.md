# 财务数据服务与 MCP 对照：Daloopa、FactSet，以及待确认的 PageIndex

调研日期：2026-10-05。范围：公开第一方文档；没有连接供应商账户、调用其数据服务或开展实测。用户提到的“Fetch Index”尚未确认具体产品；此处 FactSet 是独立参考对象，不能当作名称已确认。

## 已能确认的产品结构

| 层次 | Daloopa | FactSet |
| --- | --- | --- |
| 输入与整理 | 来自财报、新闻稿、投资者演示和部分电话会材料；产品页说明数据点经过 QA，并能回到原始文档。未公开到足以复刻的提取模型、Prompt、切片或复核算法。 | Fundamentals 公开方法说明从多种披露渠道取得材料，并将原始披露按统一方法整理以便跨公司比较。该方法介绍标明内容截至 2019 年，只能说明公开方法，不能当作当前覆盖数量或时效承诺。 |
| 数值获取 | 先查公司，再发现该公司的指标序列，最后按明确期间和序列 ID 取数。 | 既有财务、预期、价格等整理数据和 API，通过 MCP 对 Agent 开放。公开 SDK 的财务返回包含标识、日期、币种、频率等字段。 |
| 文本获取 | 文档列表、关键词查找、全文或按节读取；返回文档 ID、分类、期间、内容及链接。 | 官方说明将披露、电话会、新闻等文本标准化、向量化并补充元数据，以供 RAG 和语义检索。 |
| 证据 | 财务值有 `fundamental_id`，可生成逐值出处链接；文档检索使用文档链接。 | 此次查到的通用财务 SDK 返回没有证明“每个数值都附原始单元格位置”；需针对实际 API/MCP 返回和权限另行验证，不能据此断言全部没有溯源。 |

来源：[Daloopa MCP 产品](https://www.daloopa.com/products/mcp)、[Daloopa 工具说明](https://docs.daloopa.com/docs/mcp-prompts)、[FactSet Fundamentals 公开方法](https://insight.factset.com/resources/at-a-glance-factset-fundamental-datafeed)、[FactSet MCP 发布说明](https://investor.factset.com/news-releases/news-release-details/factset-meets-demand-ai-ready-data-first-announce-mcp-sans)、[FactSet 官方 SDK 返回模型](https://github.com/factset/enterprise-sdk/blob/main/code/python/FactSetFundamentals/v2/docs/Fundamentals.md)、[FactSet 非结构化数据方案](https://insight.factset.com/unlocking-financial-insights-from-ai-ready-unstructured-data)。

可支持的架构理解是：**原始材料 → 持续整理的数据层 → 查询 API → MCP → 分析 Agent**。这是根据公开接口归纳的边界，不是供应商内部部署图。MCP 位于服务交付层；连接 MCP 本身并不意味着实时解析年报，也不能证明其内部采用了某一种 Agent、向量库或大模型。

Daloopa 的具体使用链为：`discover_companies → discover_company_series → get_company_fundamentals`；定性材料另走 `discover_company_documents / search_documents → get_document_content`。基本面返回包含数值、期间、报表类别、序列名及出处 ID。公开读取文档说明以 20-F 为不支持示例，较大 10-K/10-Q 还会要求选择章节；因此台积电材料与 AMD 10-K 必须单独验收覆盖，不能从股票或财务指标覆盖推断全文可读。[工具协议](https://docs.daloopa.com/docs/mcp-prompts)

## 提取和审核：已知与未知

Daloopa 产品说明支持 AI 数据整理及质量控制；其数据更新功能公开提到 QA 团队、未更新单元格和原文候选提示。这足以确认质量处理和缺口提示是产品组成部分，不能推出“每一数据点都人工复核”，也没有足够公开证据描述它究竟用了什么模型、多少次复核、如何判定通过。[数据更新与 QA 说明](https://daloopa.com/blog/product-updates/enhancements-to-daloopas-new-data-disclosure-feature)

FactSet 公布了数据标准化和文本向量化路线，但本轮资料没有给出逐行抽取、人工复核比例及具体模型配置。营销页的准确率、覆盖量与本轮实测无关，不能用于判定 Uteki 已追平或落后多少。

## 对 Uteki 的验收建议

把 Data Agent 包装成可调用的数据服务，是检验“其他分析 Agent 能否独立使用”的有效方法；仍需把数据质量与调用质量分别记分。这是本调研提出的建议，尚非已实现能力。

| 要检验什么 | 相同任务示例 | 判定依据 |
| --- | --- | --- |
| 指标与期间正确 | AMD FY2023 现金、债务、股本；台积电 FY2023 对应指标 | 独立原文核对，检查公司、财年、币种、单位、合并范围、当前/非当前口径；股本金额不能替代股数。 |
| 能解释出处 | 对每个数值取回对应原文行及上下文 | 链接可打开且实际支持该值；来源版本一致。供应商门户需要权限时如实标记。 |
| 能自主发现和取数 | 只给公司、财年、问题，让新 Agent 查指标后获取数据 | 不读 Uteki 内部文件、不由 Codex 提示记录 ID；保存原始请求、响应与最终回答。 |
| 能处理不存在的数据 | 请求未覆盖年度、缺少的指标、未采纳候选 | 明确缺口或拒绝；不能取另一家公司、其他年份或把空值补零。 |
| 能计算并解释 | 现金流、资本支出及现金流差额；两家公司多期对比 | 明确公式和正负号，派生结果链接全部输入，说明比较口径限制。 |

建议每题固定同一分析模型、相同源截止日、相同财年/单位和调用额度。分别运行 Uteki MCP、供应商 MCP；可另设只读官方材料的基线。不能把多个供应商混合回答作为单家表现。若供应商无法冻结到同一截止日，单独记录“版本不可严格对齐”，不强行计算准确率差。

结果至少分别展示：正确值比例、指标覆盖率、证据支持率、缺口处理正确率、Agent 无人工提示完成率、调用次数/耗时/成本。一次完整运行仍是样本；需保存失败类别并用新问题复验，避免只优化已知答案。

有直接的方法参考：Daloopa 的 FinRetrieval 公开研究使用 500 个已知有答案的单数值题，对比 WebOnly 与 Web + MCP，并承认没有评测多步分析和缺失数据。其归因突出财年命名和指标选错。这是供应商自己的实验，不能移用成绩到 Uteki；我们应补上其未覆盖的缺口题和多步计算题。[实验与限制](https://daloopa.com/benchmark/benchmarking-ai-agents-on-financial-retrieval)

立即下一步：确认“Fetch Index”的准确名称；同时基于现有 AMD/台积电样本冻结第一批问题及原文答案。随后用只读数据服务做外部 Agent 试用，取得供应商账户与同等数据范围后再实测对照。

## 若所指产品是 PageIndex：比较检索能力

本节是对候选产品 PageIndex 的独立调研，尚未认定它就是用户说的 Fetch Index。当前官方资料给出的流程为：文档 → 树状目录与节点内容 → 分析模型沿树定位并读取 → 回答与引用。公开仓库当前 Flash 路径从文本 PDF 的版面/目录建立结构，模型负责摘要及优化；不能把所有版本都概括成“完全用模型建树”。[公开仓库与本地模式说明](https://github.com/VectifyAI/PageIndex)

接口可取得文档状态、节点/页范围、摘要/正文和页面内容。云端还提供块及边界框，本地与云端的 OCR、图像处理和引用粒度有差别。对外 Agent 可加载它的使用指令和检索工具，也可使用云端 MCP；具体工具权限需单独约束，文档上下文并不自动形成访问隔离。[文档产物](https://docs.pageindex.ai/sdk/documents)、[Agent 集成与引用](https://docs.pageindex.ai/sdk/agents)、[MCP](https://docs.pageindex.ai/mcp)

因此，它适合与 Uteki 的“找到正确原文、补全上下文、回答材料问题”对照。树索引和有引用的回答，本身不证明已经得到可跨公司比较、已核验的财务序列数据库；若要比较财务入库结果，应将后续指标映射、期间/单位转换、遗漏检查也计入评测。本轮没有安装或实跑 PageIndex，也未验证其宣传的 benchmark 成绩。

## Uteki 当前能作为外部服务交付到哪一步

2026-10-05 只读源码核对：现有 ScopedQueryDataPort 已有目录/schema、受控财务查询、原文检索/阅读/证据读取；CompanyDataCoordinator 已有获取、查询、刷新和冻结产物检查。未发现已实现的 Uteki MCP server。接口使用者仍须了解本机数据路径、scope、模型配置和已选材 job；仅有“公司 + 问题”还不能无辅助跑完整任务。

对真实 AMD main-agent-v2 候选库的只读服务探针，经目录发现和 typed query 返回了 3 条记录与 5 个证据：两期现金及一期股数。没有调用模型。返回 `complete` 仅表示明确请求的 3 项取齐；债务和股本未入库的草稿不会自动出现在已入库指标目录，必须另行返回预期覆盖和未解决项。此探针不是全新 Codex 经 MCP 完成任务的证明。

还需暴露或补齐的边界：候选状态与外围内容审核尚未统一到查询响应；AMD/TSMC 当前是不同快照，应返回各自来源句柄并分别查询；虽然获取和读取支持 20-F，typed DocumentRequest.form 枚举尚缺 20-F；已登记批次的自主选择不等于全年报选材已自动化。现有封存运行查看也不能替代运行中任务的持久状态服务。

首版工具建议（未实施）：

| 工具 | 对外目的 |
|---|---|
| discover_data | 按公司、期间、材料类型和截止日发现来源、版本与覆盖，返回稳定 scope ID |
| get_data_schema | 解释指标、实际期间、单位和原币种，提供真实字段样例 |
| query_facts | 取财务事实及明确计算，返回来源、审核状态和缺口 |
| read_source | 按明确动作查目录、搜索、读原文和证据，并支持续读 |
| request_data | 后续用于提交缺失材料获取或补充提取，返回任务 ID |
| get_job | 后续用于查询执行阶段、失败、产物和实际方法版本 |

建议先实现前四项，检验现有产物的消费能力；后两项随后检验自主生产。客户端不需要填写本机路径，也不应将整个内部规划 schema 或任意写 SQL 作为入口。MCP 是工具/资源交付协议；我们仍需定义财务语义和完成标准。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

具体盲测题：使用截至 2026-10-04 已公开的官方年度材料，比较 AMD 与台积电 FY2023 的营收、营业利润、经营现金流、资本支出与期末现金；保留原币种、真实财年日期和原文引用，并指出缺失、核验状态及无法比较的项目。首轮固定消费者模型，只提供服务工具与说明，不允许读仓库、由维护者补记录 ID 或联网补数；独立答案仅供审核端。第二轮再开放补提，并分别计算已有数据取用与新增处理的耗时/成本。

## 当前后台页面的阅读说明

用户当前 URL 指向 GOOGL 旧数据包，不是最近的 AMD 提取运行。现读该 GOOGL 年报：1,338 个原文块、111 条基础候选记录，index.diagnostics 为空；同源还记录了图片仅引用和未映射概念等其他缺口。因此 `解析诊断（0）` 不能表示没有处理问题。

| 页面文字 | 实际含义 |
|---|---|
| 解析诊断（0） | 该版本没有已记录的索引诊断；不是正确率、零错误或完成率 |
| [0].code / [0].severity | 通用字段渲染器把列表第 1 项以从零开始的数组位置显示；不是分数 |
| warning | 提醒检查某种处理行为或限制，不能直接理解为数字错误 |
| repeated_legal_headers_excluded | 重复/无标题页眉已标为 running_header，不参与正文覆盖与章节起点；原件和块仍保留 |
| 产物与覆盖 | 查看原件、索引、财务事实及财报精编分别完成到哪一步，不是覆盖率评分 |
| 查看表格与段落 | 看拆解后的原材料 |
| 查看事实/原文与核验 | 看提取记录，再核对同一数值的原文、期间、单位、口径及审核 |

阅读顺序建议：先选公司、材料、运行版本 → 查看财务事实 → 点一条数值 → 核对原文与期间/单位/口径 → 看审核及缺口；遇到异常再展开解析诊断。当前页面把程序字段与完成状态混排，是可读性问题；本轮只解释与记录建议，尚未改版。
